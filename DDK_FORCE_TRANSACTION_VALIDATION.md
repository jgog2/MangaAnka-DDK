Force Re-Audit Selected SQLite repair — final validation, 2026-10-04

Implemented and validated against the current local worktrees. The live catalog was never opened or mutated. No commit, push, tag, release, version bump, schema migration, or plugin edit was made.

1. **Root cause.** A large immutable audit JSON write spills SQLite's page cache while `WorkingSets.persist_item_audit()` owns a `BEGIN IMMEDIATE` transaction. In the existing DELETE journal mode, spill can upgrade that writer to an EXCLUSIVE lock. Pin eligibility validation opened a different catalog reader inside that same transaction. The reader waited on its own workflow's writer. This was a persistence-stage self-lock, not a write transaction held across provider/network work.

2. **Exact conflicting connection.** In the deterministic original-source trace, writer connection 9 owned the audit/problems/pin transaction; reader connection 10 was opened by `Catalog.lookup()`. Both belonged to thread 32672. In the original-source Qt reproduction, writer connection 30 and reader connection 32 both belonged to AuditWorker thread 14856. These are trace-local IDs, not IDs assigned to the user's live database. Full opening stacks, SQL templates, thread ownership, transaction order and closure records are in `build/force-transaction-evidence/large-before-trace.json` and `qt-large-before-trace.json`.

3. **Exact failing SQL.** The exception was raised by a read, after the audit write had succeeded but remained uncommitted:

   ```sql
   SELECT * FROM curated_catalog cc
   WHERE EXISTS (SELECT 1 FROM curated_fields cf WHERE cf.work_id=cc.work_id)
   ```

   Call chain: Qt `CatalogPage` More action → `MainWindow.force_reaudit_selected()` → `start_audit()` → `AuditWorker.run()` → `SearchAuditor.audit_many()` → `audit_one()` → `WorkingSets.persist_item_audit()` → `pin()` → `Acceptance.evaluate()` → `Catalog.validate()` → `rows()` → `lookup()` → new connection → SELECT. The actual audit insert and large publication JSON update occurred on the writer connection before this SELECT.

4. **Why one instance reproduces it.** The OS writer lock prevents a second writable DDK instance. The backend RLock serializes writers and is reentrant. Neither makes two separate SQLite connections the same transaction. A reader opened by the same worker can therefore block on the worker's own EXCLUSIVE writer lock. This was reproduced both in the original native EXE on a newly seeded disposable Dandadan catalog and deterministically with an otherwise ordinary publication plus 4,000,000 bytes of inert test provenance padding. Small fixtures passed because they did not trigger cache spill.

5. **Why failure recording succeeds afterward.** Original trace order was writer BEGIN IMMEDIATE → audit insert/JSON update → nested reader SELECT fails → reader closes → writer ROLLBACK → writer closes → separate failure transaction inserts `working_set_observations`, changes membership to ERROR, COMMIT, closes. The old pin is untouched. The failure handler always constructs empty provider arrays, even for a persistence-stage error; their emptiness did not establish an early provider failure. The native pre-repair reproduction produced exactly one failure observation and retained the old audit/pin, with no new partial audit.

6. **Before repair boundaries.** GUI candidate validation and confirmation finish without retaining a connection. GUI queue/event transaction commits before worker dispatch. Worker AUDITING transaction commits/closes before search. Search, enrichment, ranking, inventory qualification, reference resolution, normalization and publication evaluation run without an open catalog write transaction. The short final persistence transaction writes immutable audit/problems, updates work metadata, evaluates readiness and advances the exact membership pin. Its nested validation reader was the defect. Failure recovery already ran after rollback.

Curation post-write validation also receives its existing transaction connection. No helper in that validation chain opens a competing reader. Success still commits the audit, problems and pin together. Failure still rolls back everything before recording the error in a new short transaction. No unnecessary write transaction or backend RLock spans provider/reference work.

10. **Thread and connection ownership.** `DB.con()` opens one SQLite connection per operation on the calling thread, commits normal context exit, rolls back exceptional exit, and closes in finally. The event-relay thread opens its own brief read connections when summarizing completion. Provider threads do not receive the catalog transaction connection. The supplied connection only travels through synchronous helpers on its owning thread. No long-lived catalog connection or check_same_thread=False workaround was added.
