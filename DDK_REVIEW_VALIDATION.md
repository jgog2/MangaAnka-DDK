# DDK review workflow validation — 2026-10-02

The Problems tab now produces a summary CSV, detailed issues CSV, and paired Markdown/JSON Review Packet. It offers all-unresolved, selected-problem, and Audit-selected-title scopes, plus selected/all Markdown clipboard diagnostics. The selected-problem pane uses the same evidence builder as exports. Per-problem data includes exact affected identifiers, source titles and IDs where present, automatic/curated/effective chapter type and volume, reference values and statuses, verification, classification, next action, and a conservative command suggestion. Packet evidence is normalized; raw network payloads are not embedded.

Audit and problem row IDs remain stable within stored audits. Every new audit has a per-work revision. A database revision token changes on audits, curation events, problem dispositions, and work-count changes. A packet's guard line can precede deterministic console edits. Both Preview and Apply verify the token and audit revision; Apply checks inside its transaction. Preview validates the candidate catalog. Apply confirms the persisted identity and fields, validates the effective rows, checks foreign keys and SQLite integrity, then commits atomically. Re-audit is still required for the final network/reference result.

Health now distinguishes identity, publication, normalization, and acquisition. Strict PASS requires all four to pass and no unresolved problems; acquisition gaps can coexist with publication PASS. The latest two audits yield resolved/new/remaining problem types, metric changes, conflict counts, and health transitions in Details and packets. Unclassified acquisition may be dispositioned with an explicit reviewed reason on an exact trusted identity. True publication and identity failures cannot use this disposition. The disposition journal is append-only and carries to a later audit only when the issue signature remains exact. Show ignored and Reopen append a reversal reason and restore the problem to the queue. User-entered repeated provider patterns across distinct works are flagged for code review; no source rule is generated.

Schema v3 adds `search_audits.audit_revision` and `health_json`, classification fields on `audit_holes`, and `problem_dispositions`. The migration is additive and creates `backups/mangaanka_catalog_before_schema_v3_*.db` before changing an existing catalog. A disposable legacy-schema copy retained its work row and produced a readable pre-migration backup. The user's default catalog was not opened or modified during this pass.

Validation: 60 focused offline unit tests passed; the standalone Tk smoke test passed on a disposable database, including Audit, Problems, Database, History, and Details scrollbars, contrast, problem diagnostics, clipboard, chapter selection, command preview/apply, undo/redo, and stale audit state. Syntax compilation passed. The sandboxed Python process could not initialize its Tcl installation; the same UI smoke test passed outside that sandbox. No full MangaAnkā suite, live provider run, EXE build, commit, push, tag, or release was performed.

Remaining limits: the packet can only report provenance stored by the current audit; unavailable alternate-release/provider-split distinctions remain unclassified. Repeated provider patterns are human-entered candidates, not verified code defects. Legacy audits need a re-audit for new health and normalization evidence. A packet guard must be pasted with derived commands; unguarded manual console edits retain the existing preview/audit stale checks. The unchanged Calibre plugin does not independently consume the DDK curated catalog.
