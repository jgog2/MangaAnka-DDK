# MangaAnkā publication freshness repair — validation report

Completed October 4, 2026 against the current local worktrees. This report covers the shared publication repair and its DDK consumers; it does not repeat the earlier Qt promotion or Force Re-Audit implementation.

1. **Dandadan root cause.** Audit 18 already retained Wikipedia's explicit uncollected records for chapters 220–246. The old evaluator nevertheless counted every listed Wikipedia volume as released: volumes 1–27 versus mapped volumes 1–25, so its complete-release check failed. Release dates/status were absent from the adapter output. A second blocker required absent, untyped MangaDex fractional memberships as if they were main-sequence acquisition chapters. Those decimals have no proven main taxonomy. The repair uses positive release evidence and requires untyped fractional membership only when that identifier is actually normalized as main; missing integer chapters and explicitly identified main chapters still block. Acquisition and special diagnostics remain intact.

4. **Schema.** DDK remains schema v7. No migrations, tables, lifecycle fields, persistent coverage records or database edits were introduced. The live catalog was never opened. Audit 18 was not modified; only its user-authorized exported JSON was read, scoped to the specified work/audit.

5. **Commands.** Grammar 3 is unchanged. No commands or parser rules were added. Preview/Apply, approval, acceptance, writer locking, working-set pinning and Force Re-Audit semantics remain unchanged and passed regression coverage.

6. **Release representation.** Optional source facts are `release_date`, `release_status` and `release_evidence`. Runtime evaluation distinguishes RELEASED, FUTURE, UPCOMING, PREORDER, ANNOUNCED and LISTED_BUT_NOT_RELEASED without adding a global enum. Unknown/partial dates stay unproven. A future date defeats a positive release flag; an explicit preorder status remains unconfirmed after its scheduled date until refreshed evidence supports release. Date-only evidence may cross its date boundary.

7. **Released boundary.** Only compatible, confident Wikipedia/BOOK☆WALKER evidence satisfying existing reference contracts participates. Stale last-known-good or failed-refresh records cannot establish the boundary. Positive integer released volumes must form a complete 1…N sequence. Conflicting released/future claims fail closed. Bibliographic volumes establish release facts, never chapter membership. Future Wikipedia planned contents cannot map present acquisition chapters.

8. **Testable time.** Builder and DDK resolution accept optional `as_of`; otherwise one UTC date is captured for the audit. The resolved date is stored in existing audit JSON. Tests cover before/after a release date, unknown dates, explicit preorder after its date, invalid/partial dates and citation access-date exclusion. Stored acceptance checks retain the audit's as-of evidence.

9. **Uncollected context.** It was already available in Audit 18 with section kind, page ID, revision ID and record provenance. The parser did not lose it. The shared evaluator now also retains candidate records and failed eligibility checks for debugging, rather than showing records only after successful classification.

10. **Cross-source UNCOMPILED.** Actual trusted canonical identity and edition context, explicit Wikipedia uncollected records, a contiguous unresolved suffix, resolved provider/MangaDex/Wikipedia membership for the released structure, a complete released boundary, and absence of conflicting claims must all agree. BOOK☆WALKER can corroborate release availability but cannot manufacture membership. A null-volume tail alone remains UNMAPPED. The plugin receives trusted context from its real reference bundle, including when updating a manifest created before reference lookup finishes.

11. **Curation as anchor.** DDK lookup still proceeds through live reference resolution even when curated fields exist. Reviewed fields overlay only their scope; compatible new structure outside that scope remains effective. The shared builder also protects existing reviewed/verified chapter title and membership evidence through refresh and projection. An explicitly proven complete snapshot may acquire a larger safe current count without its old expected count becoming a ceiling.

12. **Sparse versus complete.** Sparse chapter corrections never imply coverage through their maximum chapter or volume. Complete coverage requires an explicit runtime contract with `kind=complete_publication_snapshot`, `complete=true`, and enumerated volume/chapter sets. Identity-only and absent curation are distinct. CURRENT on sparse/absent coverage is not a certification of complete publication coverage.

13. **Persistent contract inspection.** The current schema/Grammar 3 has no explicit persistent complete-coverage contract. None was added. Runtime contract support is tested but is not silently attached to existing catalog entries or generated by new commands.

14. **Legacy handling.** Existing corrections remain sparse or identity-only. No `max()` coverage boundary is inferred. Legacy expected-count disagreements remain conservative review diagnostics when no explicit complete snapshot proves an extension. They do not truncate live acquisition or reference structure.

15. **Base-plugin effective extensions.** The real plugin still follows its reference worker/service → manifest builder → acquisition/publication projection → unified-volume path. Released live memberships extend the runtime model, and proven uncollected tails receive shared projection states. No curated hit short-circuits discovery. Inspection found **no existing plugin loader for the DDK SQLite catalog**; this pass adds shared identity-validated runtime patch support and existing-manifest protection, not a new SQLite/export loader. Automatic consumption of a produced DDK catalog by Calibre remains a separate integration task.

16. **Protected conflicts.** Reviewed overlap keeps its curated value. Contradictory trusted live evidence produces CONFLICT_REVIEW and the existing REFERENCE_CONFLICT problem. Edition/work/language guards remain exact. Sparse updates cannot contaminate another edition. Source change without contradiction is nonblocking.

17. **Freshness state.** Derived runtime diagnostics expose CURRENT, EXTENSION_AVAILABLE, SOURCE_CHANGED or CONFLICT_REVIEW, together with coverage kind, extension sets, conflicts and changed sources. Catalog inspector, Details/References, raw JSON and review exports show this provenance. Freshness is not a new lifecycle/approval state. Missing membership for known released volumes uses the existing MISSING_REFERENCE_STRUCTURE category; no per-chapter issue explosion was added.
